# レイアウトの土台 — 余白・グリッド・整列・視覚的階層・情報密度

> このドキュメントは、Figmaにネイティブレイヤーを自動生成するコード生成ツールが参照する「デザイン教科書」の第1章。全ジャンル（Web / モバイルアプリ / ダッシュボード / LP など）に共通する **実装可能なレイアウトの基礎ルール** を、具体的な数値とともにまとめる。抽象論は排し、「そのままコードに落とせる値」だけを扱う。

---

## この章の要点（TL;DR）

1. **すべての寸法は8の倍数を基準に**。余白・サイズ・座標は原則 `4 / 8 / 12 / 16 / 24 / 32 / 48 / 64 ...` から選ぶ。任意の 13px, 15px, 27px は禁止。
2. **近接（proximity）で情報を束ねる**。関連要素の間隔 < 無関係要素の間隔。内側の余白 ≤ 外側の余白。
3. **階層はサイズだけで作らない**。サイズ・太さ・色/コントラスト・余白の4レバーを組み合わせる。まずグレースケールで成立させる。
4. **余白は「多すぎるくらい」から始めて削る**。窮屈さは足し算で直すより、引き算で整える。
5. **本文の行長は 45–75 文字（最適66）、行間 1.5**。コンテンツ幅は読みやすさで決める。
6. **タッチターゲットは最低 44×44pt（iOS）/ 48×48dp（Android）**。視覚要素が小さくても当たり判定は確保する。

## 8pxグリッドと余白スケール

### なぜ8なのか

ほとんどの主要デザインシステム（Material Design, IBM Carbon, Apple の暗黙的グリッド, 各種8ptガイド）は **8px（Androidでは8dp）を基本単位** に採用している。理由は明快:

- **端末のピクセル密度に強い**: 多くの端末は 1.5x / 2x で描画する。8 や 24 のような値は 1.5x（→12, 36）でも 2x（→16, 48）でも整数に割り切れ、ハーフピクセルのにじみが出にくい。
- **主要ビューポート幅と相性が良い**: 320 / 360 / 768 / 1024 / 1280 / 1440 / 1920 はいずれも8で割り切れる。
- **意思決定コストの削減**: 「12pxか14pxか」で悩む余地を消す。チーム全体（＝生成ツール）が8刻みに固定すれば、出力が常に一貫する。

Figma / Sketch のナッジ量やスナップも既定で8前提になっている。

### 標準余白スケール（このツールの正準値）

パディング・マージン・gap・アイコン/ボタンの寸法はこのスケールから選ぶ。8未満の微調整用に 4 と 2 を「サブアトミック」として許可するが、乱用しない。

| トークン | 値(px/dp) | 主な用途 |
|---|---|---|
| space-0 | 0 | 隣接・境界共有 |
| space-1 | **2** | 極小の光学調整（アイコンとラベルの間など）※例外的 |
| space-2 | **4** | インライン要素間、アイコン内パディング |
| space-3 | **8** | 密なUI内の基本間隔、タグ内パディング |
| space-4 | **12** | 小コンポーネント内パディング、リスト行の縦間隔 |
| space-5 | **16** | 標準パディング/gap（最頻出）、モバイル左右マージン |
| space-6 | **24** | カード内パディング、セクション内グループ間 |
| space-7 | **32** | セクション間、カラム間gutter（広め） |
| space-8 | **40** | 大きめの区切り |
| space-9 | **48** | セクション間（大）、ヒーロー内余白 |
| space-10 | **64** | メジャーセクション区切り |
| space-11 | **80 / 96 / 128** | ページ最上位の区切り、余裕のあるLP |

> ルール: 4と8以外は「8の倍数」を第一候補にする。12だけは頻出の例外として許可（8と16の中間として実用性が高い）。それ以外の非8倍数（例: 20, 28, 44, 52, 56, 72）は、タッチターゲットやアイコン光学サイズなど**明確な理由がある場合のみ**使う。

### スケールは等比的に間隔を空ける

小さい値は密に、大きい値は疎に刻む（4→8→12→16→24→32→48→64）。線形（8,16,24,32...のみ）だと隣接値が視覚的に見分けにくく、階層差が弱くなる。**隣り合うステップは最低でも 1.25〜1.5 倍の差** をつけると、余白の違いが「意図」として読み取れる。

## 整列とグルーピング（近接）

### 近接の原則（Proximity）

「関連する要素は近づけ、無関係な要素は離す」。人は距離が近いものを1つのグループとして知覚する。**間隔そのものが情報構造を伝える**ので、境界線や背景色より先に余白でグルーピングを表現する。

実装ルール（内側 ≤ 外側 の原則 / internal ≤ external）:

| 関係 | 推奨間隔 | 補足 |
|---|---|---|
| ラベルとその入力欄 | **4–8** | 「所属している」ことを示す最短距離 |
| 見出しと直下の本文 | **8–12** | 本文と次の見出しより必ず狭く |
| リスト項目内の要素（アイコン+テキスト） | **8–12** | |
| リスト項目どうし | **8–16** | 項目内より広く |
| フォームのフィールド群どうし | **16–24** | ラベル-入力の間隔より必ず広く |
| カード内のパディング | **16–24**（狭いUIは12） | 内容とカード縁の呼吸 |
| カードどうしの gap | **16–24** | カード内パディングと同等〜やや広め |
| セクションどうし | **32–64** | ページ最上位の区切り |

> 決定的ルール: **「あるグループ内の最大間隔」＜「そのグループと隣接グループの間隔」** を常に満たすこと。これが崩れると、どこまでが1グループか読めなくなる。

### 整列（Alignment）

- **左揃えを基本にする**。ラベル、本文、フォーム項目は左端を1本の見えない縦線に揃える。中央揃えは短い見出しやCTAなど1〜2行の要素に限定。
- **エッジを共有する**。要素の左端・右端・ベースラインをできる限り既存の整列線に合わせ、新しい整列軸を増やさない。整列軸の本数は少ないほど整って見える。
- **数値は右揃え / 桁揃え**。表やダッシュボードの数量・金額は右揃えにして桁を比較可能にする。
- **すべての座標・寸法を8グリッドにスナップ**。x, y, w, h をグリッドに乗せることで、要素間の暗黙の隙間も自動的に8の倍数になる。

### 光学調整（Optical alignment）

数学的中央 ≠ 視覚的中央になるケースがある。代表例:

- 再生アイコン（▶）など片側に重心が寄る図形は、数学的中央より **1–2px 右** に置くと中央に見える。
- 円形ボタン内のアイコンは、上下パディングを機械的に等しくするより光学的に見た目で合わせる。
- 括弧・引用符・句読点はテキストボックスからややはみ出させる（ぶら下げ）と行頭が揃って見える。

これらは「2 または 4px の例外調整」を許可する数少ない場面。

## 視覚的階層（サイズ・太さ・色・余白で作る）

### 前提: 「すべてを目立たせる＝何も目立たない」

インターフェイスの問題の大半は階層の問題。要素に優先順位を与える手段は主に4レバー。**1つに頼らず組み合わせる**のがプロの作り方。

### レバー1: サイズ（Type scale）

本文を基準（16px）に、比率で刻んだタイプスケールを使う。フリーな px 指定は禁止し、下表から選ぶ。

| 役割 | サイズ(px) | 太さ | 行間(line-height) |
|---|---|---|---|
| Display / ヒーロー | 48–64 | 700 | 1.05–1.15 |
| H1 | 32–40 | 700 | 1.15–1.2 |
| H2 | 24–28 | 600–700 | 1.2–1.3 |
| H3 | 20 | 600 | 1.3 |
| 本文(大) | 18 | 400 | 1.5 |
| **本文(標準)** | **16** | 400 | **1.5** |
| キャプション/補助 | 14 | 400 | 1.4–1.5 |
| ラベル/注記 | 12 | 500 | 1.4 |

> 見出しほど行間は詰め（1.05–1.3）、本文は広め（1.5–1.6）。大きい文字は行間を詰めないと「間延び」する。

### レバー2: 太さ（Weight）

- サイズを上げずに重要度を上げたいときは太さで差をつける。実用は **400（本文）/ 500–600（強調・小見出し）/ 700（見出し）** の3〜4段階。
- 100や200など細すぎるウェイトは小サイズで潰れるため本文には使わない。

### レバー3: 色 / コントラスト（不透明度）

「濃い＝重要、薄い＝副次」で階層を作る。色相を増やすのではなく、**同じ色の濃淡（不透明度）** で3段階に整理する。

| 役割 | 目安 | 例（ダーク文字 on 白） |
|---|---|---|
| 第1階層（主）| 高コントラスト | #1A1A1A 相当 / 不透明度 ~87–100% |
| 第2階層（副）| 中コントラスト | 不透明度 ~60–75% |
| 第3階層（補助）| 低コントラスト | 不透明度 ~38–50% |

- **本文テキストのコントラスト比は 4.5:1 以上**（WCAG AA）、大きい文字（18px以上/太字14px以上）は 3:1 以上を必ず満たす。
- 「グレー文字をグレー背景に置いて薄くする」のではなく、背景に対する不透明度で調整すると背景色が変わっても破綻しにくい。

### レバー4: 余白（Spacing）

余白そのものが階層を作る。重要ブロックの周囲に広い余白を与えると、それだけで「主役」に見える。区切り線や背景色に頼る前に、まず余白で分ける。

### 実践: グレースケールファースト

**色を最後に足す**。まず白・黒・グレーだけでレイアウトを組み、サイズ・太さ・コントラスト・余白だけで階層が成立するか確認する。色に頼らないと成立しない階層は弱い。生成ツールでも「グレースケールで検証 → アクセントカラーを1〜2色だけ適用」の順を推奨。

## 情報密度とホワイトスペース

### 「余白は多すぎるくらいから始める」

窮屈なUIを直すには、後から余白を足すより、**最初に余白を多めに取り、必要な分だけ削る**方が良い結果になる。プロの成果物は、初学者が想像するより多くのホワイトスペースを持つ。

- 迷ったら **1段広い方**を選ぶ（16か24で迷ったら24から試す）。
- ただし密度が本質のUI（データテーブル、トレーディング画面、管理ダッシュボード）は例外。1画面の情報量が価値なので、行高やパディングを詰めた「コンパクト密度」を別途用意する。

### 密度モードの目安

| モード | 行高 | セル/行の縦パディング | 用途 |
|---|---|---|---|
| コンフォート | 48–56px | 12–16 | 一般的なリスト・設定 |
| スタンダード | 40–44px | 8–12 | 標準テーブル |
| コンパクト | 32–36px | 4–8 | 大量データ・ダッシュボード |

### ホワイトスペースの使い分け

- **マクロ余白**: セクション間・主要ブロック間（32–96）。ページの「間」とリズムを作る。
- **マイクロ余白**: 行間・文字間・アイコンとラベルの間（2–12）。読みやすさを作る。

両方を意識的に設計する。マクロだけ広げてマイクロが詰まっていると「スカスカなのに読みにくい」状態になる。

## グリッドとコンテンツ幅

### レスポンシブ・レイアウトグリッド（columns / gutters / margins）

グリッドは **カラム・ガター（列間）・マージン（左右の外余白）** の3要素で構成する。Material の指針を基準にした実装値:

| ブレークポイント | 想定 | カラム数 | 左右マージン | ガター |
|---|---|---|---|---|
| ~360dp（Phone） | モバイル | **4** | **16** | 8–16 |
| 600dp+（Tablet） | タブレット | **8** | **24–32** | **24** |
| 1024–1440（Desktop） | PC | **12** | 24–64（可変） | 24–32 |

- カラム幅は**固定pxではなく%（フレキシブル）**で定義し、画面幅に追従させる。マージン/ガターは上表の固定値を使う。
- IBM Carbon の「2x Grid」も同様に **8pxのミニユニット**を全要素（タイポ・カラム・箱・アイコン）の基準幅とし、その倍数でカラムやパディングを組む。カラムには水平パディング（＝ガター）を持たせる。

### 最大コンテンツ幅

- **本文中心のページ（記事・ドキュメント）**: 本文カラムは **横 640–720px（約 45–75文字）** に制限。無限に広げない。
- **アプリ/ダッシュボードのメイン領域**: 最大 **1200–1440px** でセンタリングし、超ワイドモニタで間延びさせない。
- 横に広い画面では、テキストブロックだけ幅を絞り、レイアウト全体は広げる（テキスト幅とレイアウト幅を分離）。

### タイポグラフィと読みやすさ（数値）

| 項目 | 推奨値 | 根拠 |
|---|---|---|
| **本文行長** | 45–75文字（最適 **66**） | Bringhurst / Baymard。長すぎると行送りで視線を見失い、短すぎるとリズムが崩れる |
| モバイル本文行長 | 45–60文字 | 画面幅の制約 |
| **本文行間（line-height）** | **1.5–1.6**（単位なし） | WCAG（段落内は最低1.5倍）。可読性・アクセシビリティ両立 |
| 見出し行間 | 1.05–1.3 | 大きい字ほど詰める |
| 段落間 | 行間の 0.75–1.5 倍（例 16px本文で 12–24px） | 段落の区切りを明示 |

### タッチターゲット（必達の下限）

- **iOS（Apple HIG）**: 操作可能要素は最低 **44×44pt**。
- **Android（Material）**: 最低 **48×48dp**（物理約9mm）。隣接ターゲットは **8dp以上** 離す。頻用コントロールは 16dp+ 推奨。
- 視覚的なアイコンが 24dp、アバターが 40dp でも、**当たり判定（透明パディング含む）を44/48まで拡張**する。見た目の小ささと操作領域は分けて考える。
- WCAG 2.5.8（AA）は最低24×24pxを要求。実務では iOS 44 / Android 48 を満たせば両方クリアできる。

## よくある失敗と修正

| 症状 | 原因 | 修正（数値で） |
|---|---|---|
| 全体が窮屈で読みにくい | パディング不足 | カード内 16→24、セクション間 16→32〜48 に広げる |
| グループの境界が曖昧 | 内側と外側の余白が近い | 内側 ≤ 外側 を徹底。項目内8 / 項目間16 / グループ間24+ に段差をつける |
| 見出しが本文にくっつく | 見出し上下の余白が対称 | 見出し上=次セクションとの間隔（大）、見出し下=直下本文との間隔（小=8–12）。上>下 にする |
| 「全部大きく」で主役不在 | サイズ1本頼み | サイズは1〜2段に抑え、太さ・コントラスト・余白で差をつける |
| ラベルがどの入力のものか不明 | ラベルと入力が離れすぎ | ラベル-入力=4–8、フィールド間=16–24。前者を必ず狭く |
| 端数だらけで揃わない | 13/15/27px などの任意値 | 全寸法を8グリッドにスナップ（4は許容、12は例外OK） |
| 超ワイドで文章が読めない | 本文幅が無制限 | 本文カラムを 640–720px（66文字）に制限しセンタリング |
| 薄いグレー文字が読めない | コントラスト不足 | 本文4.5:1以上を確保。薄くするなら不透明度60%程度まで |
| ボタンが押しにくい（モバイル） | 当たり判定が小さい | 見た目が小さくても 44×44 / 48×48 の透明領域を付与、隣接は8dp+離す |
| セクションの塊感がない | マクロ余白不足 | セクション間を 32/48/64 に。区切り線より余白を優先 |
| 密度が高すぎて読み疲れる | 行高詰めすぎ | 一般リストは行高44–56、行間1.5に戻す。密度が要る画面のみコンパクト適用 |

## 生成ツール向けチェックリスト（出力前検証）

- [ ] すべての padding / margin / gap / w / h / x / y が {2,4,8,12,16,24,32,40,48,64,80,96,128} のいずれか
- [ ] 各グループで「内側の最大間隔 < 外側の間隔」が成立
- [ ] ラベル-入力 < フィールド間 < グループ間 の段差がある
- [ ] 見出しの下余白 < 上余白
- [ ] 本文 line-height 1.5、本文カラム幅 ≤ 720px（≒66文字）
- [ ] 本文コントラスト ≥ 4.5:1、大文字 ≥ 3:1
- [ ] 操作要素の当たり判定 ≥ 44×44pt（iOS）/ 48×48dp（Android）、隣接 ≥ 8dp
- [ ] 階層がグレースケールでも成立している
- [ ] 左揃え基準、整列軸は最小限
- [ ] レスポンシブ: 4/8/12カラム、マージン16/24〜32/可変、ガター8〜32
